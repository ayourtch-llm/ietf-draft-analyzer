### Unvalidated Elliptic Curve Public Key

**Severity**: critical | **Category**: MissingValidation

Demonstrates SSH ECDH key exchange vulnerability by sending an invalid elliptic curve public key (point at infinity) to check for missing validation.

**Setup**:
1. Step 1: Ensure Python 3 and the `cryptography` library are installed (`pip install cryptography`).
1. Step 2: Start a vulnerable SSH server that supports ECDH key exchange (e.g., an older OpenSSH version or a custom test server).

**If vulnerable**: The server accepts the point at infinity (0x00) as a valid public key and proceeds with key exchange, potentially sending SSH_MSG_KEX_ECDH_REPLY. This indicates missing validation per RFC 5656 Section 4.

**If patched**: The server rejects the invalid public key by sending SSH_MSG_DISCONNECT with reason code 16 (KEY_EXCHANGE_FAILED) or closes the connection immediately, indicating proper validation.

**Caveats**:
- This PoC uses the point at infinity (0x00) as the malicious key. Some implementations may handle this gracefully but still fail validation.
- The target must support ECDH with NIST P-256 (ecdh-sha2-nistp256).
- Network timeouts may occur if the server crashes or hangs during invalid key processing.
- This script does not perform full key exchange; it only tests the validation step.

### Ephemeral Key Leakage via Improper RNG

**Severity**: critical | **Category**: InformationLeak

Demonstrates SSH ephemeral key leakage by exploiting a weak/improperly seeded PRNG to predict ECDSA nonces or ECDH ephemeral keys.

**Setup**:
1. Step 1: Install dependencies: pip install pycryptodome paramiko
1. Step 2: Start a vulnerable SSH server that uses a weak PRNG for ephemeral key generation (e.g., seeded with a constant or low-entropy value).

**If vulnerable**: The script successfully predicts the ephemeral keys or ECDSA nonces due to the weak PRNG. If nonce reuse occurs, the private key is recovered, demonstrating full session compromise and potential long-term key recovery.

**If patched**: The script fails to predict the ephemeral keys or nonces because the PRNG is cryptographically secure and properly seeded. The recovered key does not match the expected value, and no session compromise occurs.

**Caveats**:
- This is a simulation. Real-world exploitation requires observing actual protocol messages and knowing the weak seed or PRNG state.
- The weak PRNG implementation is simplified for demonstration. Real vulnerabilities may involve more complex seeding issues or side-channels.
- The script assumes the attacker can predict the PRNG output. In practice, this may require additional information or side-channel data.
- The ECDSA nonce reuse attack is a classic example. Other attacks may involve partial key leakage or timing side-channels.

### Keystream Reuse via Counter Wraparound in SDCTR Mode

**Severity**: critical | **Category**: ReplayAttack

Demonstrates keystream reuse vulnerability in SDCTR mode when counter wraps around, allowing plaintext recovery via XOR of ciphertexts.

**Setup**:
1. Step 1: Install dependencies: pip install pycryptodome
1. Step 2: Run the script to simulate the vulnerability

**If vulnerable**: The script successfully recovers the plaintext by XORing the two ciphertexts. The output shows that the recovered plaintext matches the expected plaintext, demonstrating the keystream reuse vulnerability.

**If patched**: In a patched implementation, the counter would not wrap around, or rekeying would occur before 2^L blocks are encrypted. The keystream would not be reused, and XORing the ciphertexts would not reveal the plaintext.

**Caveats**:
- This is a simplified simulation of the vulnerability. Real SSH implementations use more complex counter modes and rekeying mechanisms.
- The script uses a small counter size (32-bit) for demonstration purposes. Real implementations typically use larger counters.
- The vulnerability requires the attacker to capture ciphertexts encrypted with the same keystream, which may not always be feasible in practice.

### Keystream Reuse DoS via SDCTR Misuse

**Severity**: critical | **Category**: DenialOfService

Demonstrates keystream reuse in SSH SDCTR mode by forcing encryption of >2^L blocks with the same key, allowing plaintext recovery via XOR.

**Setup**:
1. Step 1: Ensure Python 3 and `cryptography` library are installed (`pip install cryptography`).
1. Step 2: Set up a vulnerable SSH server that does not rekey before 2^L blocks (for demonstration, we simulate the server-side encryption logic locally).
1. Step 3: Run the script to generate massive traffic, trigger counter wrap-around, and demonstrate keystream reuse.

**If vulnerable**: The script will simulate counter wrap-around, causing keystream reuse. The XOR of the two ciphertexts will match the XOR of the two plaintexts, demonstrating that an attacker can recover the XOR of plaintexts and potentially decrypt sensitive data.

**If patched**: A patched SSH implementation would enforce rekeying before 2^L blocks (or 2^(L/4) as recommended), preventing keystream reuse. The counter would not wrap, and each encryption would use a unique keystream, making the XOR attack ineffective.

**Caveats**:
- This is a simulation of the cryptographic vulnerability. Real-world exploitation requires forcing a vulnerable SSH server to encrypt massive amounts of data without rekeying.
- The script uses a simulated 32-bit counter for demonstration purposes. Real SSH SDCTR uses a 64-bit counter, making wrap-around extremely difficult to trigger without a vulnerable implementation.
- The attack assumes the attacker can observe or influence the encryption of multiple messages with the same key and nonce.
- Modern SSH implementations typically enforce rekeying limits, making this vulnerability rare in practice.

### MAC Collision Replay Attack via Sequence Number Wraparound

**Severity**: high | **Category**: ReplayAttack

Demonstrates SSH MAC collision replay attack via sequence number wraparound by simulating counter overflow and packet replay.

**Setup**:
1. Step 1: Install dependencies: pip install paramiko cryptography
1. Step 2: Start a vulnerable SSH server that does not rekey after 2^32 packets (mocked in this PoC)
1. Step 3: Run the script to simulate the attack scenario

**If vulnerable**: The script simulates a sequence number wraparound and demonstrates that a replayed packet with the same MAC is accepted because the sequence number matches the wrapped value. This shows how an attacker could replay old packets if the SSH implementation does not rekey after 2^32 packets.

**If patched**: A patched SSH implementation would rekey before the sequence number wraps around, resetting the counter and invalidating old MACs. The replayed packet would be rejected because the MAC would not match the new key context.

**Caveats**:
- This PoC simulates the vulnerability by manually manipulating the sequence number counter.
- Real-world exploitation requires monitoring a connection for 2^32 packets without rekeying, which is impractical.
- The script uses a simplified MAC calculation for demonstration purposes.
- This PoC does not interact with a real SSH server but demonstrates the theoretical vulnerability.

### Rekeying Counter Race Condition

**Severity**: high | **Category**: RaceCondition

Demonstrates a race condition in SSH SDCTR rekeying where concurrent threads can exceed the 2^32 packet limit before rekeying is triggered.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: No external dependencies required; uses standard library only.
1. Step 3: Run the script to simulate the race condition in a multi-threaded SSH encryption context.

**If vulnerable**: The vulnerable implementation will show a final packet count that exceeds the 2^32 rekey threshold without triggering the rekey process. This demonstrates the race condition where multiple threads read the counter before it is incremented, potentially exceeding the limit before rekeying is initiated.

**If patched**: The safe implementation will show a final packet count that does not exceed the 2^32 rekey threshold, and the rekey process will be triggered correctly. This demonstrates that proper synchronization prevents the race condition.

**Caveats**:
- This is a simulation of the race condition, not an actual SSH implementation.
- The actual vulnerability depends on the specific SSH implementation's threading model and synchronization mechanisms.
- The script uses a simplified counter to demonstrate the concept; real SSH implementations may have more complex state management.
- The race condition may not always manifest due to thread scheduling and system load.

**Caveats**:
