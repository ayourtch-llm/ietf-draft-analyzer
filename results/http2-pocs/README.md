### HPACK Bomb / Header Table Exhaustion

**Severity**: high | **Category**: DenialOfService

Demonstrates HPACK Bomb / Header Table Exhaustion by sending large, unique header fields to fill the receiver's dynamic table.

**Setup**:
1. Step 1: Install the `hpack` library (`pip install hpack`) for correct HPACK encoding.
1. Step 2: Start a vulnerable HTTP/2 server (e.g., an older version of a web server or a custom implementation without strict header table limits).
1. Step 3: Run the script against the target server's IP and port.

**If vulnerable**: The server's memory usage increases significantly as it stores the large, unique header fields in its HPACK dynamic table. If the server has no strict limits on the dynamic table size or the number of entries, it may crash, become unresponsive, or return HTTP 431 (Request Header Fields Too Large) or HTTP 2 (Internal Server Error) responses. In severe cases, the server process might be killed by the OS due to out-of-memory conditions.

**If patched**: The server enforces strict limits on the HPACK dynamic table size (via SETTINGS_HEADER_TABLE_SIZE) and the maximum uncompressed header list size (via SETTINGS_MAX_HEADER_LIST_SIZE). It will either reject the large headers with an HTTP 431 status code, send a GOAWAY frame with error code ENHANCE_YOUR_CALM (0xB), or simply ignore the oversized entries, preventing memory exhaustion.

**Caveats**:
- This script assumes the target server supports HTTP/2 and HPACK compression.
- The effectiveness of the attack depends on the server's implementation of HPACK and its memory management.
- Some servers may have default limits that prevent the attack from succeeding without tuning.
- The script uses the `hpack` library for correct HPACK encoding. Manual encoding is complex and error-prone.
- Running this script against production systems without authorization is illegal and unethical.

### HPACK Compression Side-Channel (CRIME/BREACH-like)

**Severity**: high | **Category**: InformationLeak

Demonstrates HPACK compression side-channel (CRIME/BREACH-like) by correlating TLS record lengths with injected header data to recover secrets.

**Setup**:
1. Step 1: Install dependencies: pip install h2 cryptography
1. Step 2: Start a vulnerable HTTP/2 server that reflects attacker-controlled headers and includes a secret (e.g., session cookie) in the response headers.
1. Step 3: Ensure the server uses a shared HPACK compression context for both attacker-controlled and secret data.

**If vulnerable**: The script successfully recovers the secret data byte-by-byte. When the attacker's guess matches the secret, the HPACK compression context reuses the entry, resulting in a shorter TLS record length. The script identifies these shorter lengths and reconstructs the secret.

**If patched**: The script fails to recover the secret. The server either disables HPACK compression for sensitive data, uses separate compression contexts for attacker-controlled and secret data, or the TLS record lengths do not correlate with the attacker's guesses due to padding or other mitigations.

**Caveats**:
- This PoC assumes the attacker can observe TLS record lengths, which may require being on-path or using a timing oracle.
- The script assumes the server reflects attacker-controlled headers and includes a secret in the response headers.
- Real-world attacks may require more sophisticated techniques to handle noise, retries, and server-side mitigations.
- This script is for educational purposes only and should not be used against systems without explicit permission.

### HTTP/2 Request Smuggling via Unvalidated Header Fields

**Severity**: high | **Category**: MissingValidation

Demonstrates HTTP/2 request smuggling by sending headers with invalid characters (CR/LF/NUL/uppercase) that bypass validation during HTTP/2 to HTTP/1.1 translation.

**Setup**:
1. Step 1: Install required dependencies: pip install h2
1. Step 2: Ensure a vulnerable HTTP/2 to HTTP/1.1 intermediary or server is running on the target host/port.
1. Step 3: Run the script with the target host and port: python poc_http2_request_smuggling_unvalidated_headers.py <target_host> <target_port>

**If vulnerable**: The server accepts the HTTP/2 request with invalid headers (containing CR, LF, NUL, or uppercase characters) without returning a 400 Bad Request or PROTOCOL_ERROR. When translated to HTTP/1.1, the invalid characters act as delimiters, potentially injecting additional HTTP requests or manipulating message framing. This indicates the intermediary/server fails to validate headers per RFC 9113 Section 8.2.1 before translation.

**If patched**: The server rejects the request by returning a 400 Bad Request status code or sending a RST_STREAM with PROTOCOL_ERROR (error code 1). This indicates proper validation of header fields according to RFC 9113 Section 8.2.1, preventing the injection of invalid characters that could be exploited for request smuggling.

**Caveats**:
- Requires a target that supports HTTP/2 over TLS (h2).
- Some servers may silently drop invalid headers instead of rejecting the entire request, which still indicates a vulnerability but may not be detected by this simple check.
- The script uses the h2 library for HTTP/2 framing; ensure it's installed (pip install h2).
- Actual exploitation depends on the specific intermediary's translation behavior and the backend server's parsing of HTTP/1.1.
- This is a proof-of-concept for educational purposes; unauthorized testing against systems you don't own is illegal.

### Oversized SETTINGS_MAX_FRAME_SIZE

**Severity**: high | **Category**: OversizedPayload

Demonstrates HTTP/2 memory exhaustion by advertising the maximum SETTINGS_MAX_FRAME_SIZE and sending large DATA frames.

**Setup**:
1. Step 1: Ensure Python 3.6+ is installed with standard libraries (ssl, socket, struct).
1. Step 2: Target an HTTP/2 server (h2c or h2). For h2, ensure the server's certificate is trusted or disable verification for testing.
1. Step 3: Run the script against the target server.

**If vulnerable**: The server accepts the SETTINGS frame and allocates memory buffers up to 16MB for incoming DATA frames. When the large DATA frames are sent, the server's memory usage spikes significantly. **If patched**: The server either rejects the SETTINGS frame with a SETTINGS_MAX_FRAME_SIZE value that is too large (if it enforces internal limits), or it processes the large DATA frames using streaming techniques without allocating large contiguous memory buffers. **Caveats**:
- This script assumes the target server supports HTTP/2 and respects the SETTINGS_MAX_FRAME_SIZE parameter.
- For h2 (TLS), the server's certificate verification is disabled for testing purposes. In a real scenario, proper certificate validation should be used.
- The script sends frames sequentially. For a more impactful attack, multiple concurrent connections should be used.
- Some servers may have internal limits on frame size that are lower than the RFC maximum, which would mitigate this vulnerability.
- The script does not handle HTTP/2 flow control window updates, which may be necessary for sending large amounts of data in a real attack.

### Server Push Abuse / Reserved Stream Exhaustion

**Severity**: high | **Category**: DenialOfService

Demonstrates HTTP/2 Server Push Abuse by flooding PUSH_PROMISE frames to exhaust client reserved stream state.

**Setup**:
1. Step 1: Install dependencies: pip install h2
1. Step 2: Run the script against an HTTP/2 server that supports server push (e.g., nginx with http2_push on, or a custom vulnerable server).

**If vulnerable**: The client allocates state for each promised stream, entering the 'reserved (remote)' state. As the number of PUSH_PROMISE frames increases, the client's memory usage grows linearly. Eventually, the client may run out of memory or stream IDs, causing it to drop connections or become unresponsive to legitimate requests. The client does not close the connection because reserved streams do not count toward the concurrent stream limit.

**If patched**: The client detects the excessive number of PUSH_PROMISE frames and either resets the streams with RST_STREAM, sends a GOAWAY frame with error code ENHANCE_YOUR_CALM, or ignores the frames. The client's memory usage remains bounded, and it continues to process legitimate requests normally.

**Caveats**:
- This script uses the h2 library for HTTP/2 framing. In a real attack, raw sockets might be used to bypass library-level protections.
- The target server must support HTTP/2 and allow server push (SETTINGS_ENABLE_PUSH > 0).
- The script does not actually send the data over the network in the flood phase to avoid overwhelming the local buffer. A real exploit would send the data incrementally.
- Modern HTTP/2 clients often have built-in protections against this attack, limiting the number of reserved streams.
