### Host Key Verification Bypass

**Severity**: critical | **Category**: MissingValidation

Demonstrates SSH Host Key Verification Bypass by simulating a client that accepts an unverified host key, enabling a MitM scenario.

**Setup**:
1. Step 1: Install paramiko: pip install paramiko
1. Step 2: Ensure an SSH server is running on localhost (or modify TARGET_HOST/TARGET_PORT)
1. Step 3: Run the script to simulate a vulnerable client connection

**If vulnerable**: The script successfully connects to the SSH server and executes a command, demonstrating that the client accepted the host key without prior verification. This mimics the vulnerable behavior where a MitM attacker could inject their own host key.

**If patched**: The secure client simulation will reject the connection if the host key is not pre-verified, demonstrating the patched behavior. The vulnerable simulation will still connect, highlighting the risk of defaulting to AutoAddPolicy.

**Caveats**:
- Requires a running SSH server on the target host.
- Valid credentials must be provided for the connection to succeed.
- This PoC demonstrates the client-side vulnerability; a real MitM attack would require network positioning.
- The script uses paramiko for simplicity; raw socket implementation would be more complex but follow the same logic.

### Protocol Version Downgrade via Compatibility Mode

**Severity**: high | **Category**: Downgrade

Demonstrates SSH protocol version downgrade via 1.99 compatibility mode interception

**Setup**:
1. Step 1: Ensure Python 3 is installed with standard libraries (socket, struct, threading)
1. Step 2: Start a vulnerable SSH server with compatibility mode enabled (e.g., OpenSSH with Protocol 1,2)
1. Step 3: Run the PoC script pointing to the target SSH server

**If vulnerable**: When the target SSH server has compatibility mode enabled (supports 1.99), the attacker's proxy intercepts the connection, detects the 1.99 version string, and forces the client to negotiate using SSH 1.x protocol. The client will reconnect or continue using the older, insecure protocol, bypassing SSH 2.0 security features.

**If patched**: When the target SSH server does not support compatibility mode (1.99 disabled), the attacker's proxy cannot force a downgrade. The client will continue negotiating using SSH 2.0 protocol, and the connection will proceed with modern security features intact.

**Caveats**:
- This PoC assumes the attacker is on-path and can intercept TCP connections.
- The target SSH server must have compatibility mode enabled for the downgrade to succeed.
- The client must support SSH 1.x protocol for the downgrade to be effective.
- This is a simplified relay and may not handle all SSH protocol nuances.
- Ensure proper authorization before testing on any system.

**Severity**: high | **Category**: DenialOfService

**Setup**:
1. Step 1: Ensure Python 3 and the 'paramiko' library are installed (pip install paramiko).
1. Step 2: Set up a target SSH server (e.g., OpenSSH) without rate limiting or connection throttling for unauthenticated clients.
1. Step 3: Verify network access to the target SSH server port (default 22).

**If patched**: The SSH server will implement rate limiting or connection throttling for unauthenticated clients, preventing resource exhaustion. Connections may be dropped or delayed, and the server will maintain normal performance for legitimate users.

**Caveats**:

### Algorithm Negotiation Downgrade (Cipher/MAC/Compression)

**Severity**: high | **Category**: Downgrade

Demonstrates SSH Algorithm Negotiation Downgrade by intercepting and modifying KEXINIT messages to force 'none' encryption/MAC.

**Setup**:
1. Step 1: Install dependencies (none required, uses standard library)
1. Step 2: Start a vulnerable SSH server that supports 'none' cipher/MAC (e.g., OpenSSH with -oCiphers=none -oMACs=none)
1. Step 3: Run the script with target IP and port: python3 poc_algorithm_negotiation_downgrade.py <target_ip> <target_port>

**If vulnerable**: The server accepts the modified KEXINIT message and responds with SSH_MSG_NEWKEYS, indicating that it has agreed to use 'none' for encryption and MAC. The connection is now unencrypted and unauthenticated, allowing an attacker to intercept and modify traffic.

**If patched**: The server either disconnects with SSH_MSG_DISCONNECT or ignores the 'none' algorithms, falling back to a secure algorithm. Modern SSH implementations typically disable 'none' by default, making this attack ineffective.

**Caveats**:
- This PoC assumes the target server supports 'none' for encryption and MAC algorithms.
- Modern SSH implementations (e.g., OpenSSH 7.0+) disable 'none' by default, making this attack ineffective against up-to-date systems.
- The script does not handle key exchange or authentication, as the goal is to demonstrate the algorithm negotiation downgrade.
- Running this script against systems you do not own or have explicit permission to test may be illegal.

### Ambiguous Host Key Verification Policy

**Severity**: high | **Category**: ImplementationAmbiguity

Demonstrates how SSH clients with permissive default host key verification policies can be tricked into accepting a malicious server's key, enabling a Man-in-the-Middle attack.

**Setup**:
1. Step 1: Install dependencies: pip install paramiko
1. Step 2: Ensure you have a test SSH server or use a local mock for demonstration
1. Step 3: Run the script with appropriate target configuration

**If vulnerable**: When the target SSH client is configured with a permissive default policy (auto-accept unknown host keys), it will establish a connection to a server without verifying the host key. This allows a Man-in-the-Middle attacker to present their own host key and intercept the connection without the client raising an alert.

**If patched**: When the target SSH client is configured with a strict default policy (reject unknown host keys), it will refuse to establish a connection to a server with an unknown or unverified host key. The client will either prompt the user for explicit verification or reject the connection entirely, preventing MitM attacks.

**Caveats**:
- This PoC demonstrates the client-side vulnerability concept rather than performing an actual MitM attack
- Real exploitation requires the attacker to be on-path or able to perform DNS spoofing
- The script uses paramiko for SSH client simulation; actual exploitation would target real SSH clients
- Results may vary depending on the specific SSH client implementation and its default configuration
- Some modern SSH clients have moved towards stricter defaults, reducing the prevalence of this vulnerability

### Authentication State Bypass via Premature Connection Protocol Messages

**Setup**:
1. Step 1: Ensure Python 3 is installed.

**Caveats**:

- The script uses minimal payloads for SSH messages, which may not be fully compliant with all SSH implementations.

### Host-Based Authentication Trust Exploitation

**Severity**: high | **Category**: AuthBypass

Demonstrates SSH Host-Based Authentication Trust Exploitation by impersonating a trusted host using a compromised host key.

**Setup**:
1. Step 1: Install paramiko: pip install paramiko
1. Step 2: Generate a host key pair for the attacker to use: ssh-keygen -t rsa -b 2048 -f attacker_host_key -N ''
1. Step 3: Configure a vulnerable SSH server to enable hostbased authentication and add the attacker's public key to ~/.ssh/shosts.equiv or /etc/ssh/shosts.equiv on the server, mapping the trusted hostname to the allowed username.
1. Step 4: Ensure the server's sshd_config has 'HostbasedAuthentication yes' and 'IgnoreRhosts no'.

**If vulnerable**: The script successfully authenticates to the SSH server using only the host key, bypassing password or user public key authentication. It prints 'SUCCESS: Host-based authentication bypassed!' and executes commands as the target user.

**If patched**: The server rejects the authentication attempt, raising a paramiko.AuthenticationException. This happens if host-based authentication is disabled, the host key is not trusted, or additional authentication methods are required.

**Caveats**:
- Requires a misconfigured SSH server with HostbasedAuthentication enabled.
- The attacker must possess the private host key of a trusted client.
- The server must be configured to trust the impersonated hostname (via shosts.equiv or similar).
- Network-level checks (like IP-to-hostname verification) on the server may block the exploit if the attacker's IP doesn't match the trusted host's IP.
- This PoC uses paramiko for simplicity; real-world exploitation may require raw socket manipulation to bypass client-side checks.
