### BGP Message Header Length Field Manipulation

**Severity**: critical | **Category**: OversizedPayload

Demonstrates BGP Message Header Length Field Manipulation by sending a BGP message with a Length field exceeding the RFC 4271 maximum of 4096 octets.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Identify the IP address and port (default 179) of the target BGP speaker.
1. Step 3: Run the script with the target's IP address as an argument.

**If vulnerable**: The target BGP speaker may crash, hang, or reset the connection without sending a proper NOTIFICATION message. Alternatively, it may allocate a large buffer based on the Length field (4097 bytes) before validation, leading to resource exhaustion or out-of-bounds read/write if it attempts to read that much data from the TCP stream.

**If patched**: The target BGP speaker correctly validates the Length field upon receipt. It detects that 4097 > 4096 and immediately sends a BGP NOTIFICATION message with Error Code 1 (Message Header Error) and Error Subcode 2 (Bad Message Length), then closes the TCP connection.

**Caveats**:
- This PoC assumes the target is a BGP speaker listening on the default port 179.
- The script sends a single malicious message. In a real attack, an attacker might send multiple messages to exhaust resources.
- Some BGP implementations may silently drop invalid packets without sending a NOTIFICATION, which is a deviation from RFC 4271 but not necessarily a crash vulnerability.
- Ensure you have explicit permission to test the target system. Unauthorized testing is illegal.

### TCP MD5 Absence / Lack of Transport Authentication

**Severity**: critical | **Category**: AuthBypass

Demonstrates BGP session establishment without TCP MD5 authentication, confirming the absence of transport-layer security.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Identify a target BGP speaker IP address that is reachable.
1. Step 3: Run the script with the target IP as an argument: python3 poc_tcp_md5_absence.py <TARGET_IP>

**If vulnerable**: The script successfully establishes a TCP connection to port 179, sends a BGP OPEN message, and receives a valid BGP OPEN or KEEPALIVE response. This confirms that the target does not enforce TCP MD5 authentication, allowing an unauthenticated peer to establish a BGP session.

**If patched**: The TCP connection to port 179 is either refused, reset, or times out immediately. This indicates that the target requires TCP MD5 authentication (RFC 2385) and rejects connections that do not provide a valid MD5 signature in the TCP options.

**Caveats**:
- This PoC assumes the target is reachable and listening on port 179.
- Some firewalls or IDS/IPS systems may block unauthorized BGP connections regardless of MD5 status.
- The script uses a fake AS number and BGP ID; a real attack would use values that might be more likely to be accepted by the target's policy.
- TCP MD5 is a legacy mechanism; modern deployments may use IPsec or BGPsec instead.

### BGP Session Hijacking via OPEN Replay

**Severity**: critical | **Category**: ReplayAttack

Demonstrates BGP Session Hijacking via OPEN Replay by capturing a valid OPEN message and replaying it to establish a session.

**Setup**:
1. Step 1: Ensure you have root privileges to create raw sockets or bind to privileged ports if necessary.
1. Step 2: Set up a BGP speaker (e.g., FRRouting, Quagga, or a router) configured to accept BGP sessions from the attacker's IP.
1. Step 3: Ensure TCP MD5 authentication is disabled on the target BGP speaker.
1. Step 4: Run the script with the target IP and the IP of the legitimate peer whose OPEN message will be captured.

**If vulnerable**: The target BGP speaker accepts the replayed OPEN message and responds with a KEEPALIVE, establishing a BGP session with the attacker. This allows the attacker to send malicious UPDATE messages to hijack traffic.

**If patched**: The target BGP speaker rejects the replayed OPEN message, sending a NOTIFICATION message with an appropriate error code (e.g., Bad BGP Identifier, Bad Peer AS, or Unacceptable Hold Time) or simply closing the TCP connection.

**Caveats**:
- This PoC simulates the capture of a BGP OPEN message. In a real attack, the attacker would need to capture a valid OPEN message from a legitimate peer using packet capture tools.
- The script assumes the attacker can initiate a TCP connection to the target BGP speaker on port 179.
- The script does not handle BGP session maintenance (KEEPALIVE messages) after the initial OPEN exchange.
- The script does not implement IP spoofing. If the target validates the source IP address, the attacker must be on-path or able to spoof the IP.
- The script assumes TCP MD5 authentication is disabled on the target BGP speaker.

### BGP Route Table Overflow (Prefix Flooding)

**Severity**: high | **Category**: DenialOfService

Demonstrates BGP Route Table Overflow (Prefix Flooding) by establishing a BGP session and flooding the target with unique IP prefixes.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Ensure the target router is configured to accept BGP peering from the attacker's IP.
1. Step 3: Run the script with the target router's IP address as an argument.

**If vulnerable**: The target router will allocate memory for each advertised prefix in its Adj-RIB-In and Loc-RIB. As the number of prefixes increases, the router may experience memory exhaustion or CPU overload, leading to a Denial of Service for legitimate traffic or BGP sessions. The router may also terminate the BGP session by sending a NOTIFICATION message with Error Code Cease if a maximum prefix limit is configured and reached.

**If patched**: The target router will enforce a maximum prefix limit and either discard new prefixes or terminate the BGP session with a NOTIFICATION message (Error Code Cease) once the limit is reached. The router will not experience memory exhaustion or CPU overload, and legitimate traffic will continue to be processed normally.

**Caveats**:
- This script assumes the target router is configured to accept BGP peering from the attacker's IP.
- The script uses a fixed number of prefixes (10,000) for demonstration purposes. In a real attack, the number of prefixes would be much higher to cause significant impact.
- The script does not handle all possible BGP error conditions or edge cases.
- Running this script against a target without proper authorization is illegal and unethical.

### BGP Session Replay Attack

**Severity**: high | **Category**: ReplayAttack

Demonstrates a BGP Session Replay Attack by capturing and replaying BGP OPEN and UPDATE messages to hijack a session without TCP MD5 authentication.

**Setup**:
1. Step 1: Ensure you have root privileges to create raw sockets and bind to privileged ports.
1. Step 2: Set up a test environment with two BGP speakers (e.g., using FRRouting, Quagga, or Cisco IOSv) configured without TCP MD5 authentication.
1. Step 3: Run the script on a machine that can intercept traffic between the BGP peers (on-path) or has the ability to inject packets into the session.

**If vulnerable**: When the target BGP speaker does not have TCP MD5 authentication enabled, the replayed OPEN message will be accepted, and the session will be re-established. The replayed UPDATE messages will be processed, potentially injecting stale or malicious routing information into the target's routing table. This can lead to traffic diversion or blackholing.

**If patched**: When the target BGP speaker has TCP MD5 authentication enabled (as per RFC 2385), the replayed messages will be rejected because they lack the correct TCP MD5 signature. The target will send a NOTIFICATION message and close the connection, preventing the replay attack.

**Caveats**:
- This script requires root privileges to create raw sockets and capture traffic.
- The capture function is simplified and may not work on all network interfaces or operating systems.
- The script assumes that the attacker is on-path or can inject packets into the BGP session.
- The script does not handle all BGP message types or edge cases.
- This script is for educational and security research purposes only. Unauthorized use is illegal.

### BGP Version Downgrade Attack

**Severity**: high | **Category**: Downgrade

Demonstrates a BGP Version Downgrade Attack by intercepting and modifying the BGP OPEN message version field.

**Setup**:
1. Step 1: Ensure you have root privileges to bind to port 179 and manipulate raw TCP sockets.
1. Step 2: Set up a test BGP peer (e.g., using FRRouting, Quagga, or a router) configured to support BGP version 4.
1. Step 3: Run the script with the target BGP peer's IP address and the local IP to bind the proxy.

**If vulnerable**: The target BGP peer accepts the downgraded OPEN message with Version 3. The script prints 'SUCCESS: Target accepted downgraded BGP version!' and the BGP session proceeds using BGP-3, potentially lacking modern security features or capabilities.

**If patched**: The target BGP peer rejects the downgraded OPEN message by sending a NOTIFICATION message with Error Code 'OPEN Message Error' and Error Subcode 'Unsupported Version Number'. The script will show the target's response, and the BGP session will not be established with the downgraded version.

**Caveats**:
- This PoC requires root privileges to bind to low ports and manipulate TCP sockets.
- The target BGP peer must be configured to support multiple BGP versions for the downgrade to succeed.
- Modern BGP implementations may strictly enforce version 4 and reject lower versions, mitigating this attack.
- This script acts as a transparent proxy; the BGP client must be configured to connect to the proxy's IP and port instead of the target directly.
- BGP sessions are typically long-lived; this PoC focuses on the initial OPEN message exchange.

### BGP OPEN Message Collision State Confusion

**Severity**: high | **Category**: StateConfusion

Demonstrates BGP OPEN Message Collision State Confusion by manipulating BGP Identifiers across simultaneous TCP connections to trigger inconsistent FSM states.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Identify a target BGP speaker (e.g., a router or BGP simulator) listening on TCP port 179.
1. Step 3: Run the script with the target IP address as an argument: python3 poc_bgp_open_collision_state_confusion.py <TARGET_IP>

**If vulnerable**: If the target BGP implementation is vulnerable, it may enter an inconsistent FSM state due to the collision detection logic being triggered while processing the second OPEN message. This could result in the target dropping the legitimate connection, failing to transition to the Established state, or entering an undefined state, leading to a Denial of Service (DoS). The target might send a NOTIFICATION message with a Cease error code or simply close the connection without proper state transition.

**If patched**: If the target BGP implementation is patched, it will correctly handle the collision detection logic. It will compare the BGP Identifiers, retain the connection with the higher-valued BGP Identifier, and close the other connection with a NOTIFICATION message (Cease error code). The FSM will transition cleanly to the Idle state for the closed connection and remain in the Established state for the retained connection, without any inconsistent state or DoS.

**Caveats**:
- This PoC assumes the target BGP speaker is listening on the default port 179.
- The BGP Identifiers used in the PoC are arbitrary and may need to be adjusted based on the target's configuration.
- The delay between the two connections is set to 0.5 seconds, which may need to be tuned to reliably trigger the collision state confusion.
- The PoC does not handle all possible BGP message types or error conditions, and may fail if the target sends unexpected messages.
- Running this PoC against a production BGP speaker may cause network disruptions and should only be done in a controlled environment.
