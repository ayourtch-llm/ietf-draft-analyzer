### Missing Host Key Verification

**Severity**: critical | **Category**: MissingValidation

Demonstrates how an SSH client accepts any host key when verification is disabled, allowing MITM.

**Setup**:
1. 1. Ensure Python 3 is installed.
1. 2. Install the `cryptography` library: pip install cryptography
1. 3. (Optional) Start a local SSH server for testing, or use the script's built-in mock server mode.

**If vulnerable**: The script outputs 'VULNERABLE: Client accepted attacker's key' and '[Impact] Attacker can now decrypt and manipulate all traffic.' This demonstrates that when host key verification is disabled, the client accepts any public key presented by the server (or attacker), allowing a man-in-the-middle attack.

**If patched**: The script outputs 'SECURE: Connection rejected. Host key mismatch! Expected ..., got ...' for Scenario B. This shows that with proper verification enabled, the client detects the fake key and aborts the connection, preventing the MITM attack.

**Caveats**:
- This is a simulation of the protocol logic using Python's cryptography library. It does not perform actual network traffic interception or decryption.
- Real-world SSH clients may have additional security measures (e.g., strict host key checking by default in modern OpenSSH).
- The PoC focuses on the logical vulnerability described in RFC 4251, not a specific implementation bug.

### SSH Version Downgrade via Compatibility Flag Manipulation

**Severity**: high | **Category**: Downgrade

Demonstrates SSH banner manipulation (stripping CR/LF, setting version to 1.99) to trigger compatibility mode and potential SSH-1 fallback.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Start a local OpenSSH server with legacy SSH-1 support enabled (e.g., `sshd -d` or configure `Protocol 1,2` in sshd_config).
1. Step 3: Run this script as an MITM proxy on the loopback interface.

**If vulnerable**: The client receives the modified banner 'SSH-1.99-MITM_Downgrade_PoC\r\n'. Because the version is set to 1.99 and CR/LF handling is manipulated, a vulnerable client will detect compatibility mode. It may either immediately attempt an SSH-1 key exchange (sending SSH-1 specific packets) or close the connection and automatically reconnect using the legacy SSH-1 protocol on the same port.

**If patched**: A patched or strictly compliant SSH-2 client will reject the banner because it does not match 'SSH-2.0-*'. It will either log a version mismatch error, refuse to connect, or ignore the compatibility flag and continue with strict SSH-2 negotiation without falling back to SSH-1.

**Caveats**:
- This PoC demonstrates the *banner manipulation* step of the attack. Full SSH-1 fallback requires the client implementation to actually support legacy SSH-1 protocols.
- Modern OpenSSH clients (OpenSSH 7.4+) have largely removed SSH-1 support entirely, so this will likely result in a connection refusal rather than a successful downgrade on current systems.
- The script is a simplified MITM proxy; it does not handle full bidirectional packet inspection and modification for the entire session, only the initial identification string exchange.

### Authentication State Reset Failure

**Severity**: high | **Category**: StateConfusion

Demonstrates how changing username/service mid-authentication can bypass state flushing in vulnerable SSH servers.

**Setup**:
1. Step 1: Install the `paramiko` library (`pip install paramiko`).
1. Step 2: Set up a local test environment with a known-vulnerable or custom SSH server implementation that tracks authentication state (e.g., using `sshd_config` with a custom module, or a Python-based mock SSH server).
1. Step 3: Ensure you have valid credentials for both the initial and target users to observe the state confusion.

**If vulnerable**: The server accepts the attacker_user's password authentication even though it should have rejected it due to missing state flush. The response will be SSH_MSG_USERAUTH_SUCCESS (type 60), indicating that the server incorrectly retained victim_user's public key challenge-response state and applied it to attacker_user's password attempt.

**If patched**: The server correctly detects the username change from 'victim_user' to 'attacker_user' and flushes all accumulated authentication state. It will either disconnect (as mandated by RFC 4252) or reject the new authentication request with SSH_MSG_USERAUTH_FAILURE (type 51), preventing any state confusion.

**Caveats**:
- Modern OpenSSH implementations are patched against this specific vulnerability.
- This PoC requires a server that maintains complex internal authentication state across user changes.
- The script uses raw socket manipulation; real-world exploitation may require handling encryption keys and packet formatting more carefully.
- Always test only on systems you own or have explicit permission to test.

### Unauthenticated Key Exchange Resource Exhaustion

**Severity**: high | **Category**: DenialOfService

Demonstrates SSH unauthenticated key exchange resource exhaustion by rapidly initiating handshakes without completing authentication.

**Setup**:
1. Step 1: Ensure Python 3 is installed with standard libraries (socket, threading).
1. Step 2: Identify the target SSH server's IP address and port (default 22).
1. Step 3: Run the script with appropriate arguments. Note: This will generate significant network traffic and may be blocked by firewalls or rate limiters.

**If vulnerable**: The server will allocate memory and CPU cycles for each unauthenticated connection to perform Diffie-Hellman key exchange computations. If the number of concurrent connections is high enough and no rate limiting is in place, legitimate users may experience timeouts or be unable to establish new sessions due to resource exhaustion.

**If patched**: The server implements strict rate limiting (e.g., max 5 unauthenticated connections per IP per second), proof-of-work challenges during key exchange, or connection throttling. Legitimate users can still connect while the attack traffic is either dropped or processed slowly without impacting service availability.

**Caveats**:
- This PoC performs a simplified key exchange initiation. Real-world exploitation may require completing more of the handshake to maximize resource consumption.
- Modern SSH servers often have built-in protections against this specific DoS vector (e.g., OpenSSH's connection rate limiting).
- The script uses raw sockets and simplified packet crafting for demonstration purposes; production exploits would use full protocol implementations.
- Ensure you have explicit permission to test the target system, as this constitutes a denial-of-service attack.

### Cipher Downgrade via 'none' Algorithm Injection

**Severity**: high | **Category**: Downgrade

Demonstrates injection of the 'none' cipher into SSH_MSG_KEXINIT to force unencrypted transport layer.

**Setup**:
1. Step 1: Ensure you have a target SSH server running and network access (e.g., via `nc` or a local test server).
1. Step 2: Install Python 3. No external dependencies required; uses standard `socket`, `struct`, and `os` modules.
1. Step 3: Run the script with arguments: `python3 poc_ssh_cipher_downgrade_none.py <target_ip> <target_port>`

**If vulnerable**: The server responds with SSH_MSG_NEWKEYS (type 21), indicating it accepted the 'none' encryption algorithm. Subsequent traffic will be unencrypted.

**If patched**: The server sends an SSH_MSG_DISCONNECT (type 0x0F) or closes the connection, rejecting the 'none' cipher as per security policy.

**Caveats**:
- This PoC simulates sending a malicious KEXINIT directly. In a real attack, this requires on-path MITM capabilities to intercept and modify the legitimate client's packet.
- Modern OpenSSH servers typically disable 'none' by default unless explicitly configured in sshd_config (e.g., Ciphers none,aes256-ctr).
- The script assumes standard SSH port 22 or specified port. Adjust if necessary.

### Debug Message Information Disclosure

**Severity**: high | **Category**: InformationLeak

Demonstrates SSH debug message information disclosure by triggering debug responses during authentication to extract host-specific data.

**Setup**:
1. Step 1: Install the paramiko library (pip install paramiko).
1. Step 2: Ensure a target SSH server is running and accessible. The server must have 'PermitDebug' or equivalent debug message handling enabled in its configuration (e.g., sshd_config).

**If vulnerable**: The script will capture and display SSH_MSG_DEBUG messages or verbose logging output during the connection handshake. These messages may contain sensitive information such as internal file paths, kernel versions, specific algorithm details, or host-specific identifiers that were inadvertently included by the server's debug configuration.

**If patched**: The script completes the connection handshake without capturing any SSH_MSG_DEBUG messages containing sensitive data. The logging output remains clean of host-specific information, indicating that debug messages are properly disabled or sanitized as recommended by RFC 4251 Section 9.4.2.

**Caveats**:
- This PoC relies on the target server being configured to send debug messages (e.g., PermitDebug in sshd_config). Most production servers have this disabled by default.
- The script uses paramiko, which may not capture all low-level protocol messages depending on its internal logging configuration.
- Some information leakage might occur during specific error conditions or authentication failures rather than the initial handshake.
- This is a demonstration of the vulnerability class; actual exploitation depends on server-side implementation details.

### Missing Validation of Direct TCP/IP Forwarding Originator

**Severity**: high | **Category**: MissingValidation

Demonstrates how an authenticated SSH client can spoof originator IP/port in direct-tcpip channel requests, potentially bypassing network-level restrictions if the server lacks strict policy enforcement.

**Setup**:
1. Step 1: Install dependencies: pip install paramiko
1. Step 2: Ensure you have valid credentials for an SSH server that supports port forwarding (e.g., a standard OpenSSH server).
1. Step 3: Identify the target internal service IP and port (e.g., 192.168.1.50:80) that should be restricted.
1. Step 4: Run the script with appropriate arguments.

**If vulnerable**: The script successfully opens a direct-tcpip channel to the target host:port, indicating that the SSH server accepted the connection request with spoofed originator IP/port fields. This demonstrates missing validation of direct-tcpip forwarding originator.

**If patched**: The script fails to open the direct-tcpip channel, receiving an SSH exception or rejection from the server. This indicates that the server has proper policy enforcement and validates direct-tcpip requests against local restrictions.

**Caveats**:
- This PoC requires valid SSH credentials for authentication
- The actual spoofing capability depends on whether the client library allows overriding originator fields (paramiko uses real connection info by default)
- Real exploitation would require crafting raw SSH packets with spoofed fields, which this script demonstrates conceptually through the channel open request
- Server-side policy enforcement varies by implementation and configuration
- This PoC is for educational purposes only; unauthorized testing may violate laws and policies

### Authentication State Flush Race

**Severity**: high | **Category**: RaceCondition

Demonstrates race condition in SSH authentication state flushing by sending concurrent requests with changing usernames.

**Setup**:
1. Step 1: Install required dependencies (paramiko): pip install paramiko
1. Step 2: Ensure target SSH server is running and accessible at TARGET_HOST:TARGET_PORT
1. Step 3: Verify the target allows password or publickey authentication methods

**If vulnerable**: The server exhibits high timeout rates (>50%), inconsistent responses, or crashes when processing concurrent authentication requests with changing usernames. This indicates the state flushing logic is not atomic relative to request processing, allowing race conditions that may bypass authentication checks or cause denial of service.

**If patched**: All authentication requests are processed sequentially despite being sent concurrently. The server properly serializes state management, ensuring username/service changes trigger clean flushes before new requests are evaluated. No timeouts, errors, or inconsistent states occur during the attack.

**Caveats**:
- Real SSH servers require key exchange before authentication; this PoC assumes a test/debug environment or targets implementations that allow direct auth packet injection.
- Modern OpenSSH implementations serialize authentication requests internally despite RFC allowing pipelining, making exploitation difficult.
- The race window is extremely small and may require precise timing adjustments for different server implementations.
- This script demonstrates the theoretical vulnerability; actual exploitation depends on specific server implementation details.

### Algorithm Negotiation Ambiguity in Key Exchange

**Severity**: high | **Category**: ImplementationAmbiguity

Demonstrates SSH key exchange state desynchronization by exploiting optimistic packet guessing during algorithm negotiation.

**Setup**:
1. Step 1: Install required libraries: pip install scapy cryptography
1. Step 2: Set up a test environment with an SSH server (e.g., OpenSSH) listening on port 2222.
1. Step 3: Run the script as a man-in-the-middle between a client and the server, or simulate the attack locally by manipulating packet order.

**If vulnerable**: The target server processes the misaligned optimistic packet despite algorithm mismatch, leading to state desynchronization. This may cause connection drops, unexpected error messages, or bypass of authentication checks due to ambiguous handling of out-of-order KEX packets.

**If patched**: The target server strictly buffers and discards any optimistically sent packets that do not match the negotiated algorithm. The connection remains stable, and no state desynchronization occurs regardless of packet arrival order.

**Caveats**:
- This PoC simulates the attack vector; actual exploitation requires precise parsing of SSH KEX_INIT name-lists to force specific algorithm mismatches.
- Modern OpenSSH implementations have largely mitigated this by enforcing strict buffering and deterministic state transitions during key exchange.
- Testing should only be performed in isolated, authorized environments.

### Missing Validation of Channel Type in X11 Forwarding

**Severity**: high | **Category**: MissingValidation

Demonstrates an SSH server accepting an X11 channel open request without prior explicit X11 forwarding authorization.

**Setup**:
1. Step 1: Install the `paramiko` library (`pip install paramiko`).
1. Step 2: Start a target SSH server (e.g., OpenSSH) with X11 forwarding disabled or ensure no X11 forwarding was requested during authentication.
1. Step 3: Ensure you have valid credentials for an account on the target server.

**If vulnerable**: The server responds with SSH_MSG_CHANNEL_OPEN_CONFIRMATION, indicating it accepted the X11 channel open request despite no prior X11 forwarding being requested or authorized. This allows an attacker to potentially inject X11 traffic into the session.

**If patched**: The server responds with SSH_MSG_CHANNEL_OPEN_FAILURE (typically reason code 'prohibited' or similar), correctly rejecting the unauthorized X11 channel open request as mandated by RFC 4254 Section 6.3.2.

**Caveats**:
- This PoC requires an authenticated session, simulating a compromised client or insider threat scenario.
- Modern OpenSSH implementations strictly enforce this validation and will likely return FAILURE immediately.
- The test assumes the target SSH server supports the paramiko transport protocol version negotiation.
- X11 forwarding configuration on the server (e.g., X11Forwarding no in sshd_config) may also block this at a higher level.
