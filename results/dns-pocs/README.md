### Resource Exhaustion via Malformed RDATA Length (RDLENGTH)

**Severity**: high | **Category**: DenialOfService

Demonstrates DNS resource exhaustion by sending a query/response with an inflated RDLENGTH field that exceeds the actual message size.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Run the script with a target DNS server IP and port (defaults to localhost:53).
1. Step 3: Monitor the target server for crashes, hangs, or excessive memory usage.

**If vulnerable**: The target DNS server attempts to allocate memory or read data based on the inflated RDLENGTH (65535 bytes). This may cause a buffer over-read, excessive memory allocation, parsing loop, crash, or hang, resulting in a Denial of Service.

**If patched**: The target DNS server validates RDLENGTH against the remaining message size and available buffers. It rejects the malformed packet, logs an error, and continues operating normally without resource exhaustion.

**Caveats**:
- Requires network access to the target DNS server.
- Some modern DNS servers may silently drop malformed packets without crashing.
- Firewalls or IDS/IPS may intercept and block the malicious packet.
- Actual impact depends on the target implementation's parsing logic and memory management.

### RDLENGTH Field Manipulation

**Severity**: high | **Category**: OversizedPayload

Demonstrates DNS RDLENGTH field manipulation by sending a crafted DNS query with an inflated RDLENGTH value to trigger buffer over-read or allocation issues in vulnerable parsers.

**Setup**:
1. Step 1: Ensure Python 3 and the 'struct' module are available (standard library).
1. Step 2: Identify a target DNS server or local test resolver that may be vulnerable to RDLENGTH validation bypasses.
1. Step 3: Run the script with the target IP and port as arguments.

**If vulnerable**: The target DNS parser reads the RDLENGTH field (100 bytes) and attempts to read or allocate memory for that amount of RDATA. Since only 4 bytes are provided, the parser may read beyond the packet buffer, causing a buffer over-read, heap corruption, segmentation fault, or denial of service. The target may crash, hang, or return unexpected responses.

**If patched**: The target DNS parser validates the RDLENGTH field against the remaining bytes in the message. It detects that 100 bytes are claimed but only 4 are available, and safely rejects the packet with a format error (e.g., FORMERR) or drops it without crashing. No memory corruption occurs.

**Caveats**:
- This PoC assumes the target processes DNS answers and validates RRs. Some servers may ignore malformed answers in queries.
- The vulnerability may not trigger if the parser uses safe memory allocation or bounds checking.
- Network filters or IDS may block or alert on malformed DNS packets.
- For accurate testing, use a local vulnerable DNS resolver or a controlled lab environment.

### DNS Header Count Field Overflow

**Severity**: high | **Category**: OversizedPayload

Proof-of-concept script demonstrating DNS Header Count Field Overflow by sending a crafted DNS query with inflated QDCOUNT/ANCOUNT fields.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Identify a target DNS server (default: 127.0.0.1 or 8.8.8.8).
1. Step 3: Run the script with appropriate target IP and port.

**If vulnerable**: If the target DNS server is vulnerable, it may crash, hang, or exhibit abnormal behavior due to buffer over-read or excessive resource consumption when parsing the inflated count fields. The server might attempt to read beyond the packet boundaries or allocate excessive memory.

**If patched**: If the target DNS server is patched, it should validate the count fields against the actual message length and gracefully handle or reject the malformed packet. The server may return a SERVFAIL response or simply drop the packet without crashing.

**Caveats**:
- This PoC assumes the target DNS server is reachable and listening on the specified port.
- The inflated count value (0xFFFF) is chosen to maximize the potential impact, but smaller values may also trigger vulnerabilities depending on the implementation.
- Some DNS servers may have built-in protections against such attacks, making the vulnerability harder to trigger.
- Ensure you have permission to test against the target DNS server to avoid unauthorized access.
