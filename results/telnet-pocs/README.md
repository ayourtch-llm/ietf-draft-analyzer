### FORWARDMASK Buffer Overrun

**Severity**: critical | **Category**: MissingValidation

Demonstrates a buffer overflow in Telnet LINEMODE FORWARDMASK handling by sending an oversized mask.

**Setup**:
1. Step 1: Ensure a vulnerable Telnet server supporting LINEMODE is running on the target host.
1. Step 2: Run this script against the target's IP and port (default: localhost:23).

**If vulnerable**: The target server crashes, hangs, or exhibits undefined behavior due to the buffer overflow when processing the oversized FORWARDMASK data.

**If patched**: The target server rejects the malformed FORWARDMASK request, ignores it, or responds with an error without crashing.

**Caveats**:
- Requires a Telnet server that supports LINEMODE (RFC 1184).
- The exact crash behavior depends on the server's implementation and memory layout.
- Firewalls or network filters may block Telnet traffic.
- Some servers may silently drop malformed packets without crashing.

### Telnet Linemode Downgrade to Character-at-a-Time

**Severity**: high | **Category**: Downgrade

Demonstrates Telnet Linemode Downgrade by injecting DONT LINEMODE to force character-at-a-time mode.

**Setup**:
1. Step 1: Install a Telnet server (e.g., OpenSSH telnetd or inetutils-telnetd) on the target machine.
1. Step 2: Ensure the Telnet server is configured to support LINEMODE (RFC 1184) and allows negotiation.
1. Step 3: Run the script with the target IP and port as arguments.

**If vulnerable**: The Telnet server accepts the DONT LINEMODE command and/or the MODE=0 subnegotiation, switching to character-at-a-time mode. Subsequent input is processed character-by-character by the server, resulting in increased latency and potential input corruption for applications expecting local line editing. The test command 'whoami' will be processed in this degraded mode.

**If patched**: A properly secured Telnet server would either: 1) Reject unexpected DONT LINEMODE commands after negotiation is complete, 2) Ignore subnegotiations that attempt to clear the EDIT bit without proper authentication, or 3) Use cryptographic authentication of the negotiation phase (as recommended by using SSH instead). The connection would remain in LINEMODE with local editing enabled.

**Caveats**:
- This PoC assumes the attacker is on-path and can inject/modify Telnet negotiation commands.
- Some Telnet servers may not fully implement RFC 1184 or may have non-standard behavior.
- The script demonstrates the vulnerability but does not exploit it for malicious purposes.
- In practice, an attacker would need to intercept an existing connection or inject commands during the initial negotiation phase.
- Modern systems should use SSH instead of Telnet to prevent this and other protocol-level attacks.

### Linemode State Transition Race

**Severity**: high | **Category**: RaceCondition

Demonstrates a race condition in Telnet Linemode state transitions by rapidly sending conflicting MODE commands to desynchronize client and server states.

**Setup**:
1. Step 1: Ensure Python 3 is installed.
1. Step 2: Start a vulnerable Telnet server that supports RFC 1184 Linemode (e.g., a custom server or a legacy implementation).

**If vulnerable**: The server and client become desynchronized regarding the EDIT and TRAPSIG modes. This may result in the client ignoring local line editing or signal trapping protections, potentially allowing an attacker to bypass these security features.

**If patched**: The server correctly handles the rapid MODE commands, maintaining a synchronized state with the client. The EDIT and TRAPSIG modes remain consistent, and no security bypass occurs.

**Caveats**:
- This PoC assumes the attacker can inject or modify Telnet subnegotiation commands.
- The effectiveness of the race condition depends on network latency and the server's implementation of MODE command processing.
- A vulnerable Telnet server supporting RFC 1184 Linemode is required for testing.

### SLC Special Character Injection via State Confusion

**Severity**: high | **Category**: StateConfusion

Demonstrates Telnet LINEMODE SLC Special Character Injection via State Confusion by spoofing SLC commands to alter client-side character mappings.

**Setup**:
1. Step 1: Ensure a Telnet server supporting LINEMODE (RFC 1184) is running on the target host.
1. Step 2: Ensure the attacker machine is positioned on-path between the Telnet client and server (e.g., via ARP spoofing or network tap).
1. Step 3: Run the script with the target IP and port: python3 poc_slc_special_character_injection_via_state_confusion.py <target_ip> <target_port>

**If vulnerable**: The Telnet client accepts the spoofed SLC command and updates its local character mapping. When the user types the character 'a' (0x61), the client sends an IAC IP (Interrupt Process) command to the server instead of the literal character 'a'. The server processes this as a legitimate signal, potentially interrupting the current process or session.

**If patched**: The Telnet client either rejects the SLC command because it does not originate from the expected peer (server) or because it violates the negotiated state machine rules. The character mapping remains unchanged, and typing 'a' sends the literal character 'a' to the server.

**Caveats**:
- This PoC assumes the attacker is on-path and can inject packets into the Telnet session.
- The target Telnet server must support the LINEMODE option (RFC 1184).
- The Telnet client must accept SLC commands without strict validation of source or sequence.
- The exact behavior may vary depending on the Telnet client implementation.
- This script is for educational purposes only and should not be used against systems without explicit permission.

**Caveats**:

- The exact number of triplets needed to trigger the overflow depends on the target's implementation. Adjust 'num_triplets' as needed.

### FORWARDMASK Buffer Exhaustion

**Severity**: high | **Category**: DenialOfService

Demonstrates Telnet LINEMODE FORWARDMASK buffer exhaustion by negotiating a large mask and sending matching data to trigger excessive memory allocation.

**Setup**:
1. Step 1: Ensure a vulnerable Telnet server is running that supports LINEMODE and implements FORWARDMASK buffering.
1. Step 2: Run the script against the target server IP and port (default: localhost:23).

**If vulnerable**: The server allocates excessive memory to buffer incoming data based on the FORWARDMASK rules. Memory usage increases significantly, potentially leading to a denial of service if repeated or if the mask is large enough.

**If patched**: The server limits the size of the FORWARDMASK buffer or validates the mask to prevent excessive memory allocation. Memory usage remains stable, and the server continues to operate normally.

**Caveats**:
- This PoC assumes the server supports LINEMODE and implements FORWARDMASK buffering as described in RFC 1184.
- The impact depends on the server's implementation of buffer allocation and memory limits.
- Some servers may ignore or reject large FORWARDMASK subnegotiations, mitigating the attack.
- The script uses a fixed number of lines and mask characters; adjust these values to test different scenarios.
