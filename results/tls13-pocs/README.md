### Missing Validation of Certificate Chain

**Severity**: critical | **Category**: MissingValidation

Demonstrates a client accepting a fraudulent or expired certificate due to missing chain validation.

**Setup**:
1. Step 1: Install dependencies: pip install cryptography
1. Step 2: Run the script to generate a self-signed expired certificate and start a mock TLS server
1. Step 3: The script will attempt a TLS handshake using the vulnerable client configuration

**If vulnerable**: The client successfully completes the TLS handshake and receives the HTTP response, despite the server presenting an expired certificate. The output will show 'VULNERABILITY CONFIRMED: Client accepted expired certificate.'

**If patched**: The client will raise an ssl.SSLCertVerificationError during the handshake, aborting the connection. The output will show 'Client correctly rejected certificate: ...'

**Caveats**:
- This PoC simulates the vulnerability by explicitly disabling verification (CERT_NONE). In real-world scenarios, this vulnerability exists when a library or application fails to enforce verification despite configuration.
- The script uses a self-signed expired certificate. A real attack might involve a valid-looking but unauthorized certificate.
- Requires the 'cryptography' Python package to generate test certificates.

### Cipher Suite Downgrade to Weak Algorithms

**Severity**: critical | **Category**: Downgrade

Demonstrates a TLS downgrade attack by intercepting and modifying a ClientHello to remove strong cipher suites, forcing negotiation of weak algorithms.

**Setup**:
1. Step 1: Ensure Python 3 and the 'scapy' library are installed (`pip install scapy`).
1. Step 2: Identify a target server that supports weak cipher suites (e.g., TLS_RSA_WITH_RC4_128_SHA, TLS_RSA_WITH_DES_CBC_SHA).
1. Step 3: Run the script with the target IP and port. Note: This requires network access to the target and may require root privileges for raw socket operations depending on the OS.

**If vulnerable**: The server responds with a ServerHello (record type 0x16) after receiving the downgraded ClientHello, indicating it accepted one of the weak cipher suites (e.g., RC4 or DES). This confirms the server is vulnerable to downgrade attacks and does not enforce minimum security standards as required by RFC 8446.

**If patched**: The server responds with a TLS Alert (record type 0x15) containing either 'Insufficient Security' (alert 50) or 'Handshake Failure' (alert 40). This indicates the server correctly rejected the weak cipher suites and enforced security policies.

**Caveats**:
- This script requires network access to the target server.
- The target server must be configured to support weak cipher suites for the vulnerability to be exploitable.
- Modern TLS 1.3 implementations strictly forbid weak ciphers, so this attack is only effective against TLS 1.2 or older, or misconfigured servers.
- Running this script may require root privileges depending on the operating system and network configuration.
- This is a proof-of-concept for educational purposes only. Unauthorized testing of systems is illegal.

### 0-RTT Data Replay Attack

**Severity**: high | **Category**: ReplayAttack

Demonstrates a TLS 1.3 0-RTT Data Replay Attack by capturing and replaying a ClientHello with early data to a vulnerable server.

**Setup**:
1. Step 1: Install dependencies: pip install scapy cryptography
1. Step 2: Ensure a TLS 1.3 server is running that supports 0-RTT (e.g., nginx with ssl_early_data on, or a custom Python server using ssl module with TLS 1.3).
1. Step 3: Run the script with the target server's IP and port: python poc_0rtt_replay_attack.py <TARGET_IP> <TARGET_PORT>

**If vulnerable**: The server accepts the replayed ClientHello and processes the 0-RTT early data again. This may result in duplicate actions (e.g., double charging, duplicate requests) or resource exhaustion if the server does not implement anti-replay mechanisms like ClientHello recording or single-use tickets.

**If patched**: The server detects the replayed ClientHello (e.g., via ClientHello hash recording) and rejects the 0-RTT data, forcing a full 1-RTT handshake or dropping the connection. No duplicate processing occurs.

**Caveats**:
- This PoC assumes the attacker can capture network traffic (e.g., via ARP spoofing or compromised network device).
- The script uses scapy for packet capture and replay, which may require root privileges.
- The server must support TLS 1.3 and 0-RTT data for the attack to be relevant.
- The script does not decrypt the TLS traffic; it relies on the server's response to indicate processing.
- This is a proof-of-concept and may not work against all server configurations or network setups.

### Record Layer Overflow

**Severity**: high | **Category**: OversizedPayload

Demonstrates TLS 1.3 Record Layer Overflow by sending a TLS record with a length field exceeding the maximum allowed size (2^14 bytes for plaintext, 2^14 + 256 bytes for ciphertext).

**Setup**:
1. Step 1: Install dependencies: pip install scapy
1. Step 2: Ensure target TLS 1.3 server is running and accessible (e.g., openssl s_server or a custom TLS 1.3 server).

**If vulnerable**: If the target implementation is vulnerable, it may attempt to allocate a buffer based on the malicious length field (e.g., 16385 bytes for plaintext or 16641 bytes for ciphertext) before validating the limit. This could lead to a buffer overflow, memory exhaustion, or a denial of service (DoS) where the server hangs or crashes. The connection might not respond, or an unexpected error might occur.

**If patched**: A compliant TLS 1.3 implementation will validate the length field immediately upon receiving the record header. If the length exceeds 2^14 bytes for TLSPlaintext or 2^14 + 256 bytes for TLSCiphertext, the server MUST terminate the connection with a 'record_overflow' alert (Alert Level 2, Description 0). The script should report receiving this specific alert.

**Caveats**:
- This PoC sends raw TLS records without completing a full handshake. Some servers may drop connections or behave unexpectedly if they expect a proper handshake sequence first.
- The actual fragment sent is small (100 bytes) to avoid network timeouts, but the length field claims a much larger size. The vulnerability is in the length validation logic.
- For TLSCiphertext, the outer content type is always application_data (23), but the inner content type is encrypted. This PoC crafts the outer record structure.
- Results may vary depending on the TLS library implementation (e.g., OpenSSL, GnuTLS) and its strictness in adhering to RFC 8446.
- Ensure you have permission to test the target system. Unauthorized testing may be illegal.
